SOLUTION 1

The key to solving Two Sum efficiently is to avoid the \(O(n^2)\) brute-force search over all pairs.

  • Use a hash table H that maps values to their indices.
  • For each element nums[i], compute its complement: target − nums[i].
  • Check if the complement is already in H:
    • If yes, we have found a pair of indices.
    • If not, insert nums[i] with its index into H and continue.

This strategy lets us find the pair in linear time, \(O(n)\), on average.


TwoSum(nums, target):
  Initialize an empty hash table H
  for each index i in nums do
    complement ← target − nums[i]
    if complement exists in H then
      return [H[complement], i]
    end if
    Add (nums[i], i) to H
  end for
  return an error or empty result
  • Each hash table operation (insert or lookup) takes expected \(O(1)\) time.
  • We perform one lookup and at most one insertion per array element.
  • We traverse the array once, so total time is \(O(n)\).
  • The extra space used by the hash table is \(O(n)\) in the worst case.

SOLUTION 2

Heapify-Down is used when a key might be too large compared to its children (for example, after removing the minimum and moving the last element to the root).

  • At index i, compare the key at i with its children.
  • Find the smallest among the node and its children.
  • If one of the children is smaller than the current node:
    • Swap the current node with that child.
    • Recursively heapify-down at the child index.

Algorithm Heapify-Down(A, i):
  l = Left(i)
  r = Right(i)
  if l ≤ A.heap-size and A[l] < A[i] then
    smallest = l
  else
    smallest = i
  end if

  if r ≤ A.heap-size and A[r] < A[smallest] then
    smallest = r
  end if

  if smallest != i then
    exchange A[i] with A[smallest]
    Heapify-Down(A, smallest)
  end if

Heapify-Up is used when a key might be too small compared to its parent (for example, after inserting a new element at the bottom).

  • Start from index i (the newly inserted element).
  • While the parent exists and is larger than the current element:
    • Swap the element with its parent.
    • Update i to the parent index and continue.

Algorithm Heapify-Up(A, i):
  p = Parent(i)
  while i > 1 and A[p] > A[i] do
    exchange A[i] with A[p]
    i = p
    p = Parent(i)
  end while

SOLUTION 3

The central idea is to track how many meetings are simultaneously in progress using a min-heap of end times.

  1. Sort all meeting intervals by their start times.
  2. Use a min-heap H to store end times of meetings currently occupying rooms.
  3. For each new meeting [s, e]:
    • If the earliest finishing meeting in H ends at or before s, reuse that room (pop from H).
    • Otherwise, allocate a new room.
  4. The size of H after processing each interval is the number of rooms currently needed. The maximum size observed is the required number of rooms.

MeetingRooms(I):
  Input: Intervals I where each I[i] = [start_i, end_i]
  Output: Minimum number of meeting rooms required

  Sort I by start times
  Initialize an empty min-heap H

  for each interval [s, e] in I do
    if H is not empty and H[0] ≤ s then
      Remove the top element from H  // free the room
    end if
    Add e to H  // allocate a room for this meeting
  end for

  return size(H)  // maximum rooms needed at any point
  • Sorting the intervals by start time costs \(O(n \log n)\).
  • Each heap insertion or deletion costs \(O(\log k)\), where k is the heap size.
  • We perform at most one insertion and one deletion per interval, so heap operations total \(O(n \log k)\).
  • Since \(k \le n\), the overall time complexity is \(O(n \log n)\).

SOLUTION 4

We need to show:

  • The algorithm still produces a correctly sorted output.
  • The algorithm is no longer stable (it may change the relative order of equal elements).

Counting Sort works by:

  1. Counting occurrences of each key.
  2. Computing cumulative counts to determine final positions for each key.
  3. Placing each element into its final position based on these cumulative counts.

Changing the direction of the final placement loop (from n down to 1, to 1 up to n) does not affect the counts or the final positions of keys in the output array.

Therefore, the multiset of keys in the output and their sorted order by value remain correct.

Stability requires that equal elements appear in the output in the same relative order as in the input.

With the modified loop from j = 1 to n, later occurrences of the same key overwrite earlier ones in order, which breaks stability.

Example:

Let subscripts denote the original relative order of equal-valued elements.

Input: A = [4₁, 1, 3₁, 4₂, 3₂]

With the original stable Counting Sort (processing from n down to 1):

B = [1, 3₁, 3₂, 4₁, 4₂]

The relative order among equal elements (3₁ before 3₂, 4₁ before 4₂) is preserved.

With the modified loop (processing from 1 up to n), elements are placed into the output in increasing index order, which can reverse the relative order of duplicates.

In the example, this might result in a sorted array where:

B = [1, 3₂, 3₁, 4₂, 4₁]

Now 3₂ comes before 3₁ and 4₂ before 4₁, so equal elements do not preserve their input order.

Conclusion: The modified Counting Sort remains correct as a sorting algorithm but is no longer stable.

SOLUTION 5

  • Insertion Sort – Stable
    • Elements are only moved left past larger elements.
    • When keys are equal, the later element is never moved in front of an earlier equal element.
    • Thus, the relative order of equal elements is preserved.
  • Merge Sort – Stable
    • During merging of two sorted subarrays, when equal keys are encountered, the implementation always takes the element from the left subarray first.
    • This ensures that equal elements maintain their original left-to-right order.
  • Heapsort – Not Stable
    • Heap construction and heapify operations involve swaps that can move equal keys across non-adjacent positions.
    • These swaps can change the relative order of equal elements.
  • Quicksort – Not Stable (in general)
    • Partitioning around a pivot can rearrange equal elements across partitions in a way that does not preserve their original order.
    • Although there are stable variants, the standard in-place implementations are not stable.

EXTRA SOLUTION

As in the binary heap, we store the d-ary heap in an array A indexed from 1.

  • Parent: For node i (i > 1), its parent index is \[ \text{PARENT}(i) = \left\lfloor \frac{i}{d} \right\rfloor. \]
  • Children: For node i, its k-th child (for \(1 \le k \le d\)) has index \[ \text{CHILD}(k, i) = d \cdot i - d + 1 + k. \]
  • The root is stored at index 1.

Let n be the number of elements in the d-ary heap.

  • At level 0 (root), there is 1 node.
  • At level 1, there are at most d nodes.
  • At level 2, at most \(d^2\) nodes, and so on.

The total number of nodes up to height h is on the order of \[ 1 + d + d^2 + \cdots + d^h = \Theta(d^{h+1}). \]

Solving \(n = \Theta(d^{h+1})\) gives \[ h = \Theta(\log_d n). \]

Therefore, the height of a d-ary heap with n elements is \(\Theta(\log_d n)\).

We consider a d-ary max-heap (parent key ≥ child keys). Heapify-Down is used when the key at index i might be too small compared to its children.

  • At index i, examine all up to d children to find the largest key.
  • If one of the children has a key larger than A[i]:
    • Swap A[i] with the child that has the maximum key.
    • Recursively heapify-down at the child index.
  • If no child has a larger key, the heap property is satisfied at i.

D-ary-Heapify-Down(A, i):
  largest = i

  for k = 1 to d do
    child = CHILD(k, i)
    if child ≤ A.heap-size and A[child] > A[i] then
      if A[child] > A[largest] then
        largest = child
      end if
    end if
  end for

  if largest != i then
    exchange A[i] with A[largest]
    D-ary-Heapify-Down(A, largest)
  end if

The running time of D-ary Heapify-Down is \(O(d \log_d n)\), from two components:

  • Per-level work:
    • At each level, we scan up to d children to find the largest key.
    • This costs \(O(d)\) time per level.
  • Number of levels:
    • The height of the d-ary heap is \(\Theta(\log_d n)\).
    • The recursion (or iteration) can go down at most that many levels.

Combining these, the total time is \[ O(d) \cdot O(\log_d n) = O(d \log_d n). \]

For a d-ary max-heap, Heapify-Up is analogous to the binary case but with the generalized parent function.

  • Starting at index i, compare A[i] with its parent A[parent].
  • While i is not the root and A[i] > A[parent]:
    • Swap A[i] with A[parent].
    • Set i to parent and continue.

Because each swap moves the element up one level, and the heap height is \(\Theta(\log_d n)\), the running time of Heapify-Up is \(O(\log_d n)\).
